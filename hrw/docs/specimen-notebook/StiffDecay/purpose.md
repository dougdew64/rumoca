# StiffDecay — why this specimen exists

**Intent, not explanation.** *How* this specimen behaves is regenerated on demand from
[`trace/`](trace/) — generated by `cargo run -p hrw --example gen_trace -- StiffDecay`, and
therefore correct by construction. What **cannot** be regenerated is why someone made this file —
the code never says what it is *for*.

## Authored to trigger

**Stiffness, reduced to the smallest model that has it.** Two uncoupled decays, `exp(-t)` and
`exp(-1000t)`. The fast mode is below 1e−100 by t = 0.25 and contributes nothing to the answer
after that — yet an *explicit* method must keep `h` below roughly `2/1000` for the entire run or
the dead mode grows back and destroys the solution. That gap, between the step accuracy wants and
the step stability demands, **is** stiffness.

`BenchActuator` is already labelled "stiffness — BDF's reason to exist", and it is the honest
industrial case: a fast electrical L/R coupled to a slow rotor, 48 equations. This specimen is
the opposite trade. It is stiff in two lines, it is **uncoupled**, and its exact solution is a
pair of exponentials, so a claim about a solver's behaviour on it can be *checked*. Use
`BenchActuator` to see stiffness where it really occurs; use this one to see what stiffness is.

## Measured against truth, 2026-09-24

Rumoca 0.9.20, default settings, `t_end = 2`:

| quantity | Rumoca | `exp` | error |
|---|---|---|---|
| `slow(1)` | 0.367879139 | 0.367879441171 | −3.0e−7 |
| `slow(2)` | 0.135335749 | 0.135335283237 | +4.7e−7 |
| `fast(0.25)` | 0.000000000 | 2.67e−109 | — |

`fast` is reported as **signed** zero, negative at some samples. A tiny negative undershoot on a
mode whose true value is positive-definite is characteristic behaviour for a multistep method
stepping far beyond a dead transient; it is not an error, and it is a good first question for a
solver lab.
